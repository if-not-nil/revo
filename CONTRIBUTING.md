# contributing

thank you for considering contributing to revo

the project is so young, that even taking a stroll through any source file might yield you a good observation

a contribution anything from a pull request to an issue or a suggestion, all contributions are welcome!

## where to start

- check out [issues/TODO.md](./issues/TODO.md) for plans and pick an issue
- see the `./issues` directory

you can contribute via github, codeberg or via [emailing me a .patch](mailto:lung-notification@proton.me)

the commit etiquette is influenced by that of
[the linux jernel](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/log/)
(they have [a whole page](https://www.kernel.org/doc/html/v4.14/process/submitting-patches.html#describe-your-changes)) on that)

- every commit should at least compile
- its fine if something doesnt work in the middle of a commit chain, as long as it works by the final one
- formatted like

    ```text
    lang+repl!+diag: fix occasional combustion
    # if multiple scopes, list with + to separate them
    # if breaking change, use !

    repl would sometimes spit out nuclear codes

    fixed GH-1337 # for github issues, use GH-12 rather than #12
    ```

## developing revo

this doc describes the details behind revo's development, for contribution guidelines see [./CONTRIBUTING.md](./CONTRIBUTING.md)

### tooling

#### linting/routining

we use zlinter,

```sh
zig build lint --fix # just autofix
zig build lint # more pedantic diagnostics
```

there's a step which includes all tests, autofix, and formatting.\
it passing means "yes your code didnt break anything"

```zig
zig build chore
```

#### debugger/profiler

build with `-Dperf` and use the `--perf` flag to get the vm performance counters after a program runs

you wanna use lldb for zig. the debug build is unoptimized and keeps symbols

```sh
zig build
lldb ./zig-out/bin/revo
(lldb) run -e "spawn fn() add(20, 22)"
```

rss on macos: `/usr/bin/time -l ./zig-out/bin/revo bench/skynet.rv 2>&1 | grep maximum resident`

the mimalloc allocator (which is enabled by default) seems to be faster but doesnt entirely do as much work as the gpa

#### nm (liberevo)

the c api functions are `pub export fn` with `callconv(.c)`, and the header is autogenerated from `src/capi/header_gen.zig`, so it's always in sync with the exports

```sh
zig build lib
nm zig-out/lib/liberevo.a | rg erevo_
```

#### docs

the docs for the project itself can be linted and auto-fixed with `rumdl fmt`

docs can be generated via `revo doc` (markdown) or `revo doc --html` (html)

it will normally spit out the output directly, but `--splice` can paste into a template, replacing all that is
between `<!-- docgen:start -->` and `<!-- docgen:end -->`

it will also generate documentation for a whole directory of scripts if pointed at one

this is a fish script i use for regenerating docs

```fish
set STDOCPATH ~/projects/web/revo.lung.fyi/content/std.html
revo doc --html --splice ./src/base < "$STDOCPATH" > ./std.html
mv ./std.html $STDOCPATH
```

### about AI-generated code

~ please do not submit LLM-authored code if you do not understand it, can't explain it or have not tested it\
~ do not submit ai prose or multimedia text at all. if you don't know english, submit it in your native language and let the maintainer use their own translation tools\
~ write issue bodies in your own words\
~ disclose usage, but do not advertise the model/provider name (including via a Co-authored-by header)
